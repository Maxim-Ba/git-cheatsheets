# 05. Ежедневные команды

Принцип, который стоит переносить из учебных проектов на рабочие репозитории:
**один коммит — одна мысль**, ≈ до 3 файлов и 200 строк. Как правило, если сообщение приходится
писать с «и», это уже два коммита.

## 1. Выбирать куски, а не файлы

```bash
git add -p            # по кускам: y — взять, n — пропустить, s — разбить, e — править вручную
git diff --staged     # проверить, что попадёт в коммит
git commit
```

## 2. Сообщение коммита

```
тип(область): что сделано, в повелительном наклонении, до 72 символов

Необязательное тело: ПОЧЕМУ так (а не что — это видно в diff).
Refs: PROJ-123
```

- Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`. Область — модуль: `sdk`, `e2e`, `masking`.
- Один язык на репозиторий (в учебном проекте — английский и формат `iter N: …`; в командных репозиториях — договоритесь).
- Номер задачи, если есть трекер: многие команды пишут `PROJ-123 [Bug] …`.
- Плохо: `Fix java sdk`, `Change docs`, `Add node js`, `init`. Хорошо: `fix(sdk): flush spans before shutdown`.
- Аналогия из Node: Conventional Commits + `commitlint`/`semantic-release`.

## 3. Исправить последний коммит

```bash
git commit --amend            # правка сообщения / добавить забытый файл (git add сначала)
git commit --amend --no-edit  # то же, сообщение не менять
```

Только пока коммит **не запушен**.

## 4. Исправить более ранний коммит (вместо «Fix otel for masking» ×2)

```bash
git commit --fixup <хеш-раннего-коммита>
git rebase -i --autosquash <хеш-раннего-коммита>~1     # (rebase.autoSquash=true уже включён)
```

В редакторе ничего менять не нужно — fixup-коммиты сами встанут под свои цели. Сохранить и закрыть.

## 5. Ветки

```bash
git switch -c feature/short-name      # новая ветка от текущего места
git fetch --prune                     # обновить origin/* и убрать удалённые
git branch --merged master            # какие ветки уже слиты → можно удалять: git branch -d <имя>
git branch -vv                        # у каких веток есть/нет upstream
```

Правило: ветка живёт днями, а не неделями; непушенная ветка существует в единственной копии.

## 6. Stash без забытых хвостов

```bash
git stash push -m "wip: что и зачем"   # всегда с сообщением
git stash list
git stash pop                          # вернуть и удалить
git stash drop 'stash@{0}'             # удалить без возврата
```

Если в stash лежит что-то дольше дня — сделайте из этого ветку: `git stash branch wip/name`.

## 7. «Закрытие дня» — 30 секунд

```bash
git status                  # нет ли незакоммиченного и неотслеживаемого
git stash list              # нет ли забытого
git branch -vv              # нет ли веток без upstream
git push                    # всё, что готово
```

Именно это спасает заметки, которые неделями лежат без коммита, и ветки, существующие в единственной копии.

## 8. Отмена и восстановление

```bash
git restore <файл>                  # выбросить правки в рабочей папке
git restore --staged <файл>         # убрать из индекса, правки оставить
git reset --soft HEAD~1             # отменить коммит, правки остаются в индексе
git reflog                          # журнал «где был HEAD» — спасает после ошибочного reset/rebase
git switch -c rescue <хеш>          # вернуть потерянный коммит из reflog
```

## 9. Найти, где сломалось

```bash
git bisect start
git bisect bad                      # текущая версия сломана
git bisect good <старый-хеш>        # а эта была рабочей
# git сам проверит середину; говорите good/bad, пока не покажет виновный коммит
git bisect reset
```

Работает ровно потому, что коммиты атомарные: гигантский коммит на 12 тысяч строк бисектом не разобрать.

## 10. Секреты

Не коммитить: `.env`, `*.pem`, `*.key`, токены. Коммитить только `.env.example`.
Если секрет уже ушёл в коммит — его надо **отозвать/сменить**, удаление из истории не отменяет утечку.
Автопроверка перед коммитом: pre-commit hook с gitleaks (аналог `husky` в Node).
