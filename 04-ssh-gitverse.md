# 04. SSH-доступ к git-хостингу (на примере gitverse.ru)

## Симптом

```
$ ssh -T git@gitverse.ru
git@gitverse.ru: Permission denied (publickey).
```

И то же самое в любом репозитории с SSH-адресом (`git ls-remote origin`, `git push`, `git fetch`).
Если ошибка во **всех** репозиториях на машине, проблема не в конкретном репозитории, а в ключах:
сервер не узнаёт ни один из ключей, которые предлагает клиент.

Диагностика — посмотреть, какие ключи клиент предлагает и чем отвечает сервер:

```bash
ls ~/.ssh                                          # какие ключи вообще есть
ssh-keygen -lf ~/.ssh/id_ed25519.pub               # отпечаток (fingerprint) открытого ключа
ssh -vT git@gitverse.ru 2>&1 | grep -Ei 'identity file|offering|will attempt|authenticated|denied'
```

Типичные причины «Permission denied (publickey)»: ключ не добавлен в аккаунт на хостинге (удалён,
никогда не добавлялся с этой машины или добавлен в другой аккаунт); в адресе не тот пользователь
(должен быть `git`); у закрытого ключа слишком широкие права.

## Шаг 1. Проверьте, какие ключи зарегистрированы

В веб-интерфейсе хостинга откройте настройки профиля, раздел с SSH-ключами (точное название
пункта проверьте в интерфейсе) и сравните отпечатки с теми, что показал `ssh-keygen -lf`.
Если у вас несколько аккаунтов (личный и рабочий) — убедитесь, что ключ добавлен именно в тот,
у которого есть доступ к нужной организации.

## Шаг 2. Добавьте открытый ключ

Покажите **открытый** ключ (файл `.pub`) и вставьте его целиком в настройки хостинга. Закрытый
`id_ed25519` (без `.pub`) никому не отправляйте и никуда не вставляйте.

```powershell
Get-Content $HOME\.ssh\id_ed25519.pub
```

Рекомендуется ed25519 (короче и современнее, чем rsa). Новый ключ — по одному на машину:

```powershell
ssh-keygen -t ed25519 -C "<имя-машины>" -f $HOME\.ssh\id_ed25519_gitverse
```

Парольная фраза желательна. Открытый ключ — `id_ed25519_gitverse.pub`, его и добавляете.
Подпись `-C` — просто метка, чтобы в списке ключей было видно, какая машина какая.

## Шаг 3. Явно привяжите ключ к хосту (`~/.ssh/config`)

Создайте `~/.ssh/config` (Windows: `C:\Users\<имя>\.ssh\config`), шаблон: [templates/ssh_config](templates/ssh_config):

```
Host gitverse.ru
    HostName gitverse.ru
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
```

`IdentitiesOnly yes` — не перебирать все ключи подряд (у некоторых серверов лимит попыток).
Если сгенерировали новый — подставьте его имя в `IdentityFile`.

## Шаг 4. Проверка

```bash
ssh -T git@gitverse.ru                 # ждём приветствие от сервера, а не Permission denied
ssh -vT git@gitverse.ru 2>&1 | grep -Ei 'offering|authenticated|denied'
git ls-remote --heads origin           # внутри любого репозитория
```

Если после добавления ключа всё ещё `Permission denied`:

- ключ добавлен не в тот аккаунт или не сохранён — перепроверьте отпечаток;
- пользователь в адресе должен быть `git` (`git@gitverse.ru:…`);
- добавили недавно — иногда нужна минута;
- права на закрытый ключ: на Windows файл не должен быть доступен другим пользователям
  (`icacls $HOME\.ssh\id_ed25519 /inheritance:r /grant:r "$($env:USERNAME):F"`).

## Шаг 5. Опционально: ssh-agent на Windows (если у ключа есть пароль)

Служба `ssh-agent` в Windows по умолчанию отключена. Включить (PowerShell **от администратора**):

```powershell
Set-Service ssh-agent -StartupType Manual
Start-Service ssh-agent
ssh-add $HOME\.ssh\id_ed25519
```

Нюанс: Git for Windows приносит **свой** `ssh` (`/usr/bin/ssh`), а служба относится к системному
OpenSSH (`C:\Windows\System32\OpenSSH\ssh.exe`). Чтобы git использовал системный клиент и агент:

```bash
git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"
```

Без пароля у ключа агент не нужен, пропустите этот шаг.

## Запасной вариант: HTTPS + токен

Если SSH починить не получается, можно работать по HTTPS через Git Credential Manager:

```bash
git remote set-url origin https://gitverse.ru/<организация>/<репозиторий>.git
git push -u origin <ветка>      # спросит логин и персональный токен — вводите их сами в окне менеджера
```

Токен создаётся в настройках профиля на хостинге. Не вставляйте токен в URL remote'а и не коммитьте его.

## Первый push нового локального репозитория

1. Убедитесь, что репозиторий на хостинге **пустой** (создан без README/LICENSE). Если там уже есть
   начальный коммит, обычный push будет отклонён: истории не связаны.
   Посмотреть: `git ls-remote --heads origin` — пустой вывод = пустой репозиторий.
2. Перед пушем проверьте, что именно попадёт на сервер: нет ли в индексе секретов (`.env`, ключей,
   реальных паролей в конфигах и файлах стендов), только ли нужные файлы инструментов.
3. Пуш: `git push -u origin <ветка>`.

Если сервер отвечает «rejected (fetch first)» или «unrelated histories» — на сервере уже что-то есть.
Не используйте `--force`. Сначала `git fetch origin` и посмотрите `git log origin/<ветка> --oneline`.

## Что делать на каждой машине

Повторите шаги 1–4: один ключ на машину, каждый добавлен на хостинг со своей меткой.
Тогда потерянный ноутбук отзывается удалением одного ключа, а не всех.
